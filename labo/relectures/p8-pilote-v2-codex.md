## Findings

**F1 — P2, preflight blocker: all exploration/validation result CSVs have incorrect field boundaries.** `labo/src/main.rs:354` and `labo/src/main.rs:378` interpolate `Case` directly into comma-separated rows, while `labo/src/pilote.rs:81` renders it as `(W0,L0)`, containing an unquoted comma. The headers at `labo/src/main.rs:373` and `labo/src/main.rs:375` each allocate one column for `case`. Protocol: §6.2 (complete reporting of all four cases), §6.3–§6.5 (selection and validation reporting), with metric definitions in §5.3–§5.4.

Reproduced with the authorized smoke command, output `/tmp/codex-pilote-smoke-382081`:

- `exploration.csv`: header has 13 fields; all 64 data rows have 14.
- `exploration-summary.csv`: header has 10 fields; all four data rows have 11.
- Example row prefix: `(W0,L0),900,0.5,...`. A header-based CSV reader assigns `case=(W0`, `root=L0)`, `Ret_aux=900`, and shifts every remaining measurement.
- `validation.csv` and `validation-summary.csv` use the same faulty writers (`labo/src/main.rs:466`, `labo/src/main.rs:468`) and would have the same defect if validation is reached. This branch was inspected, not exercised by this smoke run.

The internal statistics and candidate selection do not consume these CSVs, so their calculations are unaffected; the saved measurement tables are nevertheless structurally incorrect. Values remain recoverable, but a known reporting defect should be fixed before producing the one-shot immutable results. Quote/escape the case field correctly, or write separate W/L columns with matching headers, and verify the generated tables with a CSV parser on technical roots.

**F2 — Low, nonblocking: the exposed embedded Organism is not a complete updated episode state.** `labo/src/pilote.rs:148`, `labo/src/pilote.rs:184`, and `labo/src/pilote.rs:191` keep the operative baseline, utilities and episode count in `Learner`, while `Learner.organism.baseline()`, `.utilities()` and `.age()` remain at birth values. The compatibility test at `labo/src/pilote.rs:625` compares the external baseline/utilities and weights, not complete Organism state. Protocol: §4's unchanged SPEC constants and §4.2; `SPEC_GENOME.md` §6.2–§6.3.

This does not change any current pilot measurement: all updates use the external baseline, utility is maintained externally with the required formula, age is tracked by `updates`, renewal is disabled, and forward/backward do not read the stale fields. However, serializing the embedded Organism or calling its learning/renewal methods later would use inconsistent state. The claimed equivalence should be understood as numerical learning equivalence for the currently used fields, not complete serialized-state equivalence. No engine modification is needed or recommended.
